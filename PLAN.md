# MapleStorage. Grandis Token Tracker

## Context

You're a long-time GMS MapleStory player who runs weekly bosses across multiple geared characters (farming the same boss on several "mules" for extra drops is standard endgame practice) and have no unified view of how close you are to a full redemption set for each Eternal-set boss token, across all of them. Today that means logging into every character individually and manually tallying, this app replaces that with screenshot uploads parsed into a single cross-character progress view.

GMS has no official Nexon data API (confirmed, only KMS/TMS/MSEA do), so screenshot parsing is the only viable data source, not a shortcut around one. This project started fully greenfield.

**Screenshots are parsed with classical computer vision, not a vision LLM (replaced 2026-07-12).** This reverses the plan's founding assumption, and the reversal is the single most consequential change the project has made, most of this document was written on the other premise, so read the "Screenshot parsing" section below before trusting any older paragraph about prompts, schemas, or token costs.

Claude vision was built (M3, on `m3-screenshot-ingestion`) and was **consistently inaccurate** on the stack-count numbers. Classical CV reads the same screenshots **exactly**: 16/16 token counts correct across all three real reference screenshots, zero false positives across 128 slots × 6 tokens, plus the character HUD. It works because MapleStory is not a photograph, the client draws its UI at a fixed pixel size (the inventory slot pitch is 46px regardless of screen resolution) and renders each item icon pixel-identically every time. Once the slot grid is located, identifying an item is a **lookup**, not a recognition problem. See `vision/README.md` and the research spike on `spike/classical-cv-inventory` for the full findings.

Consequences that ripple through the rest of this plan: **$0 per screenshot** instead of ~$0.017–0.045; deterministic (the same screenshot always yields the same answer, so a wrong read is a bug you can fix, not a sample you re-roll); no third-party call in the request path; and nothing left to meter, the `UsageLedger` was dropped entirely on 2026-07-12 (see M3).

**Be precise about what problem this solves (revised 2026-07-10)**: Nexon's forums have a running complaint thread ("Unclog our inventories") about untradeable-item clutter, and players have explicitly proposed an account-wide storage/consolidation system as the fix, a request only Nexon can build, since it requires moving items between characters server-side, which no third-party tool can do. **This app doesn't solve that.** It solves a narrower, adjacent problem that happens to share the same root frustration: not being able to see your total redemption progress across characters without checking each one individually. That's a real value, but a different one from freeing up inventory slots, the project's earlier framing conflated the two, worth correcting rather than carrying forward. Critically, the real third-party tools players already use (MapleHub, MapleTools, MS Tracker) are all boss-clear/EXP/HEXA/ranking trackers built on the Nexon Open API, and confirmed via research: **that API does not expose inventory/item contents in any region that has it**, so while this app doesn't solve inventory overflow, cross-character redemption-progress visibility specifically is still unaddressed by any existing tool.

**Scope note (narrowed back down 2026-07-10)**: this project briefly broadened (2026-07-07) from the 6 untradeable Eternal-set boss tokens to a general, user-curated item catalog spanning consumables and Etc-tab drop items. That broader version surfaced real problems on closer design work, a growable, per-user item catalog needed active curation (search/add flows, icon-collision handling, an open-ended "discovery worklist" for unidentified items) and dragged in a video-based tooltip-capture pipeline to read expiration dates on items that, on inspection, weren't even part of the original 6 tokens. None of that scope is worth the complexity for a use case validated at the *token* level, not the general-inventory level, the token catalog is fixed, small, and every one of the open risks the broader version carried (icon-matching accuracy at 50-150 items/user, expiration-tracking UX, discovery-worklist clustering) simply don't apply at a fixed set of 6. Scope is back to tokens only.

**Stack decision**: you're a mobile engineer with strong Kotlin/Compose expertise, not a JS/TS background. The backend and future native iOS/Android apps should play to that strength via Kotlin Multiplatform. The web frontend, however, stays on Next.js/React rather than Compose Multiplatform for Web, because Compose Web is still Beta and (critically) **does not yet officially support drag-and-drop**, which lands directly on this app's bulk-upload feature (dragging 15+ screenshots at once). Splitting the stack this way puts each piece on its strongest footing: Kotlin where it's your expertise and where Kotlin Multiplatform's shared-code story is real (backend ↔ future mobile), and the most battle-tested option (Next.js) for the web layer you're shipping first and that needs mature file-upload/drag-and-drop UX.

You're also explicitly using this project to build resume-relevant AWS skills, which is why several choices below favor the more resume-weighty AWS-native option over a simpler/cheaper alternative, with real recurring cost (~$25-45/month for backend infra) accepted deliberately.

| DB access (Kotlin) | **Exposed** (JetBrains' Kotlin SQL library) + **Flyway** for migrations | Kotlin-native equivalent of Prisma's query layer. Python rather than a JVM port (JavaCV) because the CV is *not* frozen, an item catalog, boss-clear parsing and further screens are all still ahead, and Fargate cost is identical either way (~+$1.60/mo for the memory bump both options need). | Mobile (future) | **Kotlin Multiplatform + Compose Multiplatform** (native iOS/Android, not Web) | The real payoff of the Kotlin-first choice, a shared Kotlin module (data models, Ktor Client-based API client, business logic) usable by both the backend (JVM target) and native mobile apps, not just similar code in two languages. |

Two deployables instead of one (Ktor service + Next.js site) means CORS configuration and running two dev servers locally. Going full-AWS on the backend adds real infrastructure surface beyond that: a VPC with public/private subnets, security groups, an ECR repo, and IAM roles all need to exist before the first deploy. Provision these via an IaC tool (**Terraform** is the pragmatic default, being cloud-agnostic and the most broadly recognized on resumes) rather than clicking through the AWS console by hand. This is real added complexity over a simpler PaaS's git-push simplicity. Accepted deliberately here since building that infrastructure knowledge is the point.

**Do not resize screenshots client-side (corrected 2026-07-12).** The original instruction here was to canvas-resize to ~1600px wide before upload, to hold down vision-LLM token cost. That is now exactly backwards: the stack-count digits are an **11px bitmap font**, and they do not survive resampling. At **0.95× every count already reads as garbage**. The 1600px cap put our own sample screenshots at 0.68× and 0.49×, where one is rejected outright and the other cannot even locate the inventory grid. Classical CV has no token cost, so the resize bought nothing and broke everything.

JPEG *compression* is still applied and is safe as long as the pixel grid is untouched: quality **75–95** reads every count correctly (measured at every integer quality); below ~72 it becomes unreliable. `frontend/lib/compress-image.ts` now draws 1:1 at quality 0.92, a 3MB PNG lands at 200–680KB. A capture that has been **shrunk** is refused; a rescaled one is read at its own scale. (Reversed since this was written. See the note at the top.)

## Character creation & the Nexon avatar lookup

**Default flow is manual-add-by-name, not screenshot-derived.** Adding a character means typing the in-game name; screenshots are only ever used afterward to *match* inventory data to an already-known character, never to create one. This was validated directly against a real endpoint during planning (2026-07-06):

- `GET https://www.nexon.com/api/maplestory/no-auth/ranking/v2/na?type=world&id={worldId}&page_index=1&character_name={name}`. No API key required, filters to the named character (confirmed via `character_name=Kraane` returning `totalCount: 1`). Returns `level`, `jobName`, `worldID`, `exp`, and `characterImgURL`.
- `characterImgURL` points to `https://msavatar1.nexon.net/Character/{encoded}.png`. Nexon's own avatar-rendering CDN (the same one mapleranks proxies). Confirmed directly fetchable with no auth/hotlink-referrer restriction, returns a real ~96x96 character sprite PNG.
- This is an **undocumented endpoint the nexon.com website itself uses**, not the official versioned OpenAPI (which is KMS-only and requires a key). Treat it as unofficial and add a fallback path (manual level entry, no sprite) for when a name isn't found or the endpoint changes/breaks.
- Ktor calls this server-side when a character is added, storing `level`/`jobName`/`worldName`/`spriteImgUrl` directly on the `Characters` row. Re-fetch on demand (e.g. a "refresh" action) rather than on a schedule. Gear/level changes don't need to be real-time here, screenshots remain the source of truth for token counts.
- **[SUPERSEDED] "Rather than on a schedule" and "directly fetchable" both changed (2026-08-11).** The sprite URL encodes the outfit, so a player changing clothes silently strands the stored URL, and nothing tells us when they have: there is now a daily re-ask (`SpriteRefreshJob`). And the bytes are no longer hotlinked from the browser. Nexon serves them with **no cache headers at all** (verified live: content-type, date, content-length, nothing else), so a browser cannot reuse one across a reload and every visit to a party page refetched every sprite. They are proxied and stored by us instead, keyed by a hash of the source URL and served `immutable` (`V53__character_sprite_cache.sql`). The manual refresh action still exists; it is no longer the only thing that keeps a sprite current.

## Screenshot ingestion & parsing pipeline

**Rewritten 2026-07-12.** Everything below the transport bullet used to describe a Claude call with a forced tool-use JSON schema, per-image cost, a semaphore over concurrent API calls, and a Batches API path for bulk drops. None of that exists any more. The parse is now local, deterministic, free, and takes ~0.3s of CPU, which deletes most of the machinery this section used to need.

- **Upload transport**: unchanged in shape. Next.js requests a presigned S3 upload URL from Ktor, the client uploads directly to S3, then calls a Ktor endpoint with the object keys plus an optional pinned `characterId`.
- **The parse itself** lives in `vision/` (see `vision/README.md`) and is called by `backend/.../services/VisionServiceClient.kt` over loopback. Three stages, and the design of each is a finding, not a preference:
  1. **Find the 16×8 slot lattice.** A slot's interior is a flat grey (~226) and every boundary is a fixed ridge whose dark flanks fall *outside* that grey band, so thresholding to the interior severs the cells from each other and each slot falls out as its own connected component. The recovered pitch doubles as the screenshot's scale.
  2. **Identify each slot's item.** A cheap 16×16 descriptor shortlists candidates for all 128 slots in one matmul; only the top 3 per slot get an exact masked correlation. Cost is **flat in catalog size** (231ms at 6 items, 273ms at 500), the naive one-`matchTemplate`-per-item approach was O(N) and would have been ~38s at 500.
  3. **Read the stack count** by correlating the client's own 10 digit glyphs. **Tesseract scores 2/12 here**, an 11px proportional bitmap font over icon art is nothing like the scanned text it is trained for. Matching the known glyphs scores 68/68.
- **The character HUD** (`Lv.287 acornacorn`) is read with the *opposite* method, and the contrast is the point: it is ~20px anti-aliased proportional text on a dark plate, which is exactly Tesseract's home turf, it reads the raw crop **exactly**, and every binarisation we tried made it *worse*. Locating it is where CV earns its keep: the HUD is anchored to the game window, not the screenshot, so we template-match the fixed-pixel `Lv.` prefix and read the line beside it.
- **The trap worth recording**: naive multi-scale template matching **does not work**. Sliding the icons over the whole image across a range of scales collapses off-native. At 0.85× the separation between a token that is *present* and one that is *absent* is **−0.02**, i.e. indistinguishable. The fix is to remove both degrees of freedom: the grid pins the scale, and per-slot attribution pins the location.
- **No concurrency machinery needed.** The semaphore-capped fan-out and the Batches API threshold both existed to ration calls to a paid, rate-limited, slow third-party API. A local 0.3s CPU parse needs neither. Bulk uploads are just a loop; the "watch it resolve live" UX in `WEB-UI-SPEC.md` gets *better*, not worse, because every row resolves in under a second.
- **Usage tracking**: none. `UsageLedger` was dropped (V5, 2026-07-12). It was kept for a while on the theory that *upload volume* is still what a quota would meter, but it was recording zeros, and a table of zeros invites someone to believe it is measuring something. Volume can be counted from `screenshots` if it is ever wanted.
- **Character match, not silent character creation**: unchanged, and the CV pipeline preserves the contract exactly. `characterHud` is `null` when no HUD is in frame (a tightly-cropped upload). **What that now routes to changed on 2026-07-12**: if the user pinned a character, it is `MATCHED` and the counts are written, because nothing in the image contradicts them (see M3). Only an *unpinned* screenshot with no HUD is `NEEDS_REVIEW`. There, genuinely nobody knows whose it is. The pin-vs-HUD `MISMATCH` flow and the one-click "new character detected" confirm flow (2026-07-08) are untouched.
- **[SUPERSEDED] We no longer refuse a capture we can actually read.** The accuracy figure below (70-77%) was measured through the parser's own resampling step, so it recorded the damage the parser was doing to itself. A real Parsec capture at 1.326x, refused outright, had every item and every count legible in the file. Rescaled captures are now read at their own scale; only a *downscaled* one is refused, because that genuinely discards pixels. We do still refuse to report a count we cannot read. The original text: a capture that is not at the client's native scale (shrunk before upload, or taken at a fractionally-scaled display resolution) is rejected with a 422 and a message telling the user what to change. It was briefly designed to return those counts with a `needsReview` flag instead; that was a half-measure, the review UI can only re-attribute a screenshot to a different character, it has no way to correct a *count*, so the dubious number would have been written anyway. For an app whose entire value is accurate counts, "you have 8" when you have 9 is worse than "we could not read this". MapleStory's own UI Optimization (exact 2× pixel doubling) is explicitly *not* caught by this, it downsamples back losslessly.

## Local development & pre-production

**Added 2026-07-12, because the project had no way to run itself.** The deploy pipeline has never gone green, so nothing had ever started the backend against a real database and a real parser and checked that the pieces fit.

`docker-compose.yml` + `scripts/smoke.sh` bring up Postgres + vision + backend and assert 7 things in about a minute. Including that a real screenshot parses to the right HUD and all five counts, and that Flyway migrations actually applied.

The compose file **mirrors ECS rather than approximating it**: the backend joins the vision container's *network namespace* (what `awsvpc` does), so it reaches the parser on `127.0.0.1` for the same reason it will in production. A compose file on separate networks talking to `http://vision:8000` would pass every check and quietly fail to test the thing that has to work.

It earned its keep on the first run, finding a bug that **would have failed every deploy and that no test could catch**: Ktor's `buildFatJar` shades every dependency into one archive and *overwrites* duplicate `META-INF/services` files instead of concatenating them. Flyway registers its scanners and database handlers through exactly that mechanism, so the deployed jar shipped with an empty plugin registry and the app died on boot (`Unknown prefix for location (should be one of ):`, an empty list). Tests run on an unshaded classpath and passed the whole time. The Dockerfile now ships the `application` plugin's distribution instead, which never merges service files at all.

(a) `aws_ecs_service.task_definition` pointed at the Terraform-managed revision while `deploy-backend.yml` registers its own SHA-tagged revision. (b) `ecs.tf` pins both containers to `:latest`, but `terraform apply` creates ECR repos *empty*, a service created against a nonexistent image cannot start a task, and on a first deploy the circuit breaker has no previous revision to roll back to. `infra/bootstrap-images.sh` does it in the order that works: create repos (targeted) → seed an image in each → apply the rest.    - **The last of Claude removed 2026-07-12.** Replacing the parser had only replaced the *call site*; everything around it still described the old system. Deleted: `AnthropicClaudeVisionService` (nothing constructed it), `Env.anthropicApiKey` (nothing read it, the backend had not needed a key to boot for some time and nobody noticed), the model-name plumbing threaded through routing purely to reach `estimateCostUsd(model, 0, 0)`, and the `UsageLedger` table itself (V5). Renamed `ClaudeVisionService` → `ScreenshotParser` and `screenshots.raw_model_response` → `raw_parse_result`. **Names that outlive the thing they describe are not cosmetic**: token persistence stayed silently broken for days partly because the code around the join still talked about a model echoing display names back, so nobody reading it had reason to doubt what it was matching on.
   - **A pin now attributes on its own (2026-07-12).** `decideOutcome` tested for a missing HUD *before* it looked at the pin, so a cropped inventory went to `NEEDS_REVIEW` even when the user had explicitly said whose it was, the parser read every count perfectly and then asked you to name a character you had just named. The rule it enforced ("a pin is only ever a cross-check target, never a blind attribution source") came from the vision-model era, when the parser could hallucinate a name and the pin existed to catch it. **It inverted the trust.** A pin is a human telling us the answer; a HUD is something we inferred from pixels. The pin is the stronger signal, and the HUD's real job is to *contradict* it. `MISMATCH` (the case that rule was actually protecting) is untouched. A pin that cannot be resolved (deleted, or not the caller's) gets its own branch, because falling through to HUD attribution there would quietly save to whoever the HUD names.

See M2), a batch review screen (per-image status, editable). **The semaphore cap and the Batches API threshold are both deleted**. They existed to ration calls to a paid, rate-limited, slow API. A local 0.3s parse is just a loop, and every row resolves in under a second.

Cross-character dashboard**: aggregate view grouped by boss/token, with an inline "progress toward next set" badge per row and freshness labels. **The icon-matching validation half of this milestone is done** (2026-07-12): 16/16 counts across three real screenshots, zero false positives, plus 14,995/14,995 on a synthetic decoder sweep. 8. **M7. Polish**: retry/error UX, manual correction without re-upload, responsive/mobile-friendly CSS (stopgap before a native app exists), screenshot history management.
9. **M8 (future, out of MVP scope). Kotlin Multiplatform mobile**: extract the shared data models + Ktor Client-based API client from the backend project into a shared Gradle module; build native Android/iOS apps with Compose Multiplatform consuming it.
10. **M9 (future, blocked on a pricing decision). Monetization**: Stripe integration, plan tiers, and quota enforcement. **The economics changed materially on 2026-07-12**: parsing is now free and local, so there is no per-screenshot marginal cost to recover. Usage-based pricing loses its main justification; whatever is charged for is the *product*, not the compute. The `UsageLedger` this milestone once assumed is gone (V5), it was metering zeros. If metering returns it should be built against something that actually costs money. Still deliberately unscoped until a model is chosen.
